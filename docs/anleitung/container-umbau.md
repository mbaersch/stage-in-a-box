# Auftragsart Container-Umbau

Steht im Auftrag **Art: Container-Umbau**, geht es nicht um eine einzelne Journey, sondern darum, dass ein Umbau im GTM (von Hand oder über die Tag Manager API, ein MCP oder ein CLI wie die [GTM CLI von owntag](https://github.com/owntag/gtm-cli)) nichts verliert: gleiche Requests an gleiche Konten, gleicher Consent, nur die erwarteten Unterschiede. Eine Aufzeichnung ist dafür optional. Die Phasen gelten wie bei anderen Tracking-Tests; Tests bauen nach [`tests-bauen.md`](tests-bauen.md), Baselines nach [`baseline.md`](baseline.md).

1. **Katalog statt Aufzeichnung:** Seiten mit eigenen Triggern plus Auslöser für Klick- und Event-Trigger. Steht nichts im Auftrag, aus dem Container ableiten: Container-Export aus GTM (*Verwaltung → Container exportieren*, JSON mit `containerVersion.trigger`) oder dieselben Trigger über die Tag Manager API bzw. ein Werkzeug, das der Mensch dafür nutzt. Relevant sind Filter auf `{{Click URL}}`, `{{Click Classes}}`, `{{Page Path}}` und Custom Events. Den Katalog in Phase 1 zur Bestätigung vorlegen. Trigger, die nur auf anderen Domains greifen, als nicht testbar nennen.
2. **Auslöser ohne passende Elemente:** `await stage.linkKlicken(page, 'tel:+49…')` bzw. mit `{ attribute: { class: 'btn btn-primary' } }`, `await stage.dataLayerPush(page, { event: 'formSubmission' })`. Je Auslöser ein `test.step`, danach `stage.warteAufRuhe()`.
3. **Ein Test je Consent-Szenario**, jeweils mit eigener Baseline (`vergleicheMitBaseline('Umbau – nur Google Ads')`). Die Szenarien stehen im Auftrag; „alle ablehnen“ erwartet null Tracking-Requests. Szenarien herstellen: [`varianten.md`](varianten.md), „Consent-Varianten“.
3a. **Bedingungen und Prüfungen aus dem Auftrag gehören in den Baseline-Test**, nicht nur als mitlaufende Option. Die Baseline meldet einen fehlenden Parameter (z. B. `gclid`) nur als Hinweis; ein Umbau, der eine Klick-ID verliert, bliebe grün. Deshalb bei „Landung über eine Anzeige“ je Klick-ID `stage.erwarteKlickId(id, { dienst, ab })` mit `ab` vor der Conversion, bei angekreuzten Prüfungen `stageOptionen.pruefungen` (z. B. `deduplizierung`, Dienste ohne Conversions API im Server-Container in `ausnahmen`).
4. **Vorher:** Baselines gegen den Ist-Stand ziehen (in der Regel der Live-Container, GTM-Vorschau-Link im Auftrag leer) und wie in Phase 3 abgleichen, bis sie sauber sind.
5. **Nachher, vor dem Veröffentlichen:** Vorschau-Link des Workspaces als GTM-Vorschau-Link unter Einstellungen in den Auftrag, dieselben Tests laufen gegen die Vorschau (Injection) und vergleichen mit den Baselines von vorher. Prüfen, dass die Vorschau wirklich geladen ist. Debug-Mode-Grenze beachten ([`gtm-vorschau.md`](gtm-vorschau.md)).
6. **Bericht:** jede Abweichung einordnen als erwartet (steht unter „Erwartete Unterschiede“) oder unerwartet. Rote Abweichungen, die erwartet sind, nicht durch neues Ziehen der Baseline verdecken, sondern benennen; erst nach Freigabe durch den Menschen und nach der Veröffentlichung die Baseline neu ziehen.

Der Modus ist `durchlassen` wie bei jeder Baseline: Conversions bei synthetischen Klicks gehen echt raus. Im Auftrag klären, ob das in Ordnung ist (Testtraffic erkennbar?), sonst die Läufe auf Remarketing und Seitenaufrufe beschränken.
